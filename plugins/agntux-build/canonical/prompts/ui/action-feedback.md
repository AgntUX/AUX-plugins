# Action Feedback

## Action Feedback Patterns (Summary)

**Every user action follows a lifecycle: idle → loading → success | error.** All four states must have distinct, visible UI representations. Users must never wonder "did it work?" after taking an action.

**Action Feedback Requirements (per interaction):**
For each user interaction that triggers `sendFollowUpMessage` or `callTool`, define:
- **Idle/default state**: How the action button looks at rest (enabled, no activity indicators)
- **Loading state**: What the user sees while processing (e.g., button shows spinner and is disabled)
- **Success state**: What the user sees on success (e.g., status badge changes from amber "Pending" to green "Replied", confirmation text appears, item visually de-emphasized)
- **Error state**: What the user sees on failure (e.g., red error text appears near the action, button re-enables for retry)
- **widgetState change**: Which fields change and to what values

**Key Patterns:**
- **Per-item state tracking**: For list/card UIs, track status per item: `Record<string, { status: 'pending' | 'success' | 'error', isSending: boolean, error?: string }>`
- **Status badge transitions**: amber "Pending" → green "Replied" / "Filed" / "Complete"
- **Visual de-emphasis**: Completed items at 60% opacity or moved to a "handled" section
- **Counter updates**: Header counts update immediately (e.g., "3 pending" → "2 pending")
- **Inline errors**: Error messages appear near the failed action, NOT as a global error state
- **Retry affordance**: On error, the action button returns to its enabled state so the user can retry

**Action types — compound is subdivided for publishing verbs:**

The two-way dichotomy (`silent persistence` / `compound`) still classifies the coarse category of every row. For publishing verbs, `compound` is subdivided so the spec can mark whether the user has already approved the payload:

1. **`silent persistence`** — UI-only state change (toggle done, rename, reorder, hide, dismiss, set preference). Host calls the file tool and stops. Unchanged.
2. **`compound (autosend)`** — publishes/sends/writes to a third-party OR sends an email, AND the user has already authored or explicitly approved the exact payload in a prior UI step (clicked "Send" on a draft they already saw). Host executes the publish immediately.
3. **`compound (draft-for-review)`** — host generates the payload (a reply, an email body, a post). The component renders a review UI showing the generated content, and a SEPARATE `compound (autosend)` action fires only when the user clicks Send on that draft.

Non-publishing compound actions (create Jira ticket, refresh a cache, run a computation that does not publish content to a human audience) may remain tagged simply `compound` — the subdivision is mandatory only when a row publishes externally.

**Default rule for publishing verbs.** Any envelope containing a third-party publish call (`chat.postMessage`, `send_email`, social post, comment/reply, DM, notification) defaults to `compound (draft-for-review)` UNLESS the user clicked Send on a draft they already saw on-screen. Verbs that trigger this default: reply, post, send, notify, alert, ping, comment, email, dm, challenge, escalate, respond, message. "Challenge decision" / "Ping for commitment" / any generated-reply flow ALL belong in draft-for-review.

**Decision tree:**

> Does the user see the final content before the external call fires?
> - YES → `compound (autosend)`.
> - NO → must be `compound (draft-for-review)`, paired with a linked `compound (autosend)` row that fires only on the explicit Send click.

**Anti-patterns:**
- A "Challenge decision" row that calls `chat.postMessage` immediately with generated text — autoposts a message the user never saw.
- A "Ping for commitment" row that sends an autogenerated DM on click — same bug.
- Any single-row `Reply` envelope that generates body text AND calls `chat.postMessage` in one step.

**Opened State Rendering (handoff contract from spec → ui-designer → coder):**

Whenever an action row classifies as `compound (draft-for-review)`, opens an inline form, surfaces a confirmation micro-surface, or otherwise reveals an interactive surface (modal, drawer, draft panel, undo toast), the corresponding UI MUST expose the OPENED state, not just the trigger:

- The **ui-designer** renders BOTH the idle trigger AND at least one example of the OPENED state in the static `ui-design.html`.
- The **coder** implements both the trigger and the opened-state UI in the React component.

Showing only the trigger leaves the coder to imagine the opened UX and routinely results in autosend bugs (e.g., a "Challenge" button rendered without its draft panel ships as an autopost). The split between trigger and opened state is the whole point of the draft-for-review classification.

**Canonical two-row pattern for challenge/ping/reply-with-generation:**

```
| Challenge decision (draft) | compound (draft-for-review) | host drafts a reply questioning the decision; component renders review UI | "Draft a challenge reply for thread @id:<id>. Render the draft in the review panel. DO NOT post." |
| Challenge decision (send)  | compound (autosend)         | user clicks Send on the rendered draft | "Post the approved draft for thread @id:<id> via chat.postMessage. Then append a metadata-only entry to drafts-sent.md." |
```

The first row never calls `chat.postMessage`; the second row never generates text (the text is already on screen, already approved). The split is the whole point.

**Sendoff format (sigil envelope — authoritative rule for Section 5 Action table):**

Every `sendFollowUpMessage` intent that embeds user-entered text (title, description, workstream, name, search query) MUST use `@key:value` sigils matching the Section 14 file schema. Quoted-string interpolation (`title='${data.title}'`, `to '{new title}'`) is **forbidden** — apostrophes, newlines, and backslashes in real user values silently corrupt the payload (e.g., `John's birthday` breaks the format).

Good (sigil envelope, matches tasks.md schema):
```
"User created a new task. Prepend to tasks.md:
@id:{newId} @workstream:{ws} @priority:{p} @due:{d} {inline(title)}
Do not add any commentary after completing the update."
```

Bad (quoted interpolation — breaks on apostrophes):
```
"User created task: title='{title}', description='{description}'. ..."
```

Use the `inline(s)` helper for single-line user text (titles, names) and the `block(s)` helper for multi-line user text (descriptions, notes) — see the coder's Action Feedback Patterns for the helper implementation. The Section 5 Action table's `sendFollowUpMessage intent` column is the literal reference the skill-writer and coder inherit, so sigil-envelope shape must be baked in at spec time.

## Action Feedback Patterns

**CRITICAL: Every user action must follow the lifecycle: idle → loading → success | error.** Users must see immediate, visible feedback for every action they take. "No console errors" is NOT sufficient — the user must see confirmation that their action worked.

### Action types — compound is subdivided for publishing verbs

The base dichotomy is `silent persistence` / `compound`. Publishing-verb rows MUST use the finer-grained subdivision of compound:

1. **`silent persistence`** — UI-only state change (toggle, rename, reorder, dismiss, set preference). Host calls the file tool and stops.
2. **`compound (autosend)`** — publishes/sends externally AND the user has already authored or explicitly approved the payload (e.g., clicked Send on a draft already on screen).
3. **`compound (draft-for-review)`** — host generates the payload, the component renders review UI, and a SEPARATE autosend action fires only on explicit user approval.

Non-publishing compound actions (create ticket, refresh cache, run computation) may stay tagged `compound` without subdivision.

**Default rule for publishing verbs.** Any envelope containing a third-party publish call (`chat.postMessage`, `send_email`, comment/reply/post/dm/notify/alert/ping/challenge/escalate/respond/message) defaults to `compound (draft-for-review)` unless the user clicked Send on a draft they already saw.

**Decision tree:** Does the user see the final content before the external call fires? YES → autosend. NO → must be draft-for-review + linked send action.

**Anti-patterns (each is a correctness bug):**
- A "Challenge decision" button that autoposts generated text.
- A "Ping for commitment" button that autosends a generated DM.
- A single-row `Reply` that both generates body text AND calls `chat.postMessage` — split into two rows (draft-for-review + autosend) so the user actually approves the content.

### Compound Action Splitting (autosend + log metadata)

**CRITICAL: A compound action that combines BOTH (a) publishing user-authored content to a third party AND (b) appending metadata to an observation log MUST be implemented as TWO sequential `sendFollowUpMessage` calls — never a single envelope.**

**Why this rule exists.** If both intents share one envelope and the envelope carries the user's raw text via `${block(replyText)}` or `${inline(replyText)}`, the host will typically write the ENTIRE envelope contents — including the raw text — into the log file. The instruction "Do NOT include the text in the log" embedded inside the same envelope is easy to miss at host-execution time, and the user's private reply text ends up persisted in `drafts-sent.md`, `activity.md`, `patterns.md`, or similar. Splitting into two calls makes the metadata envelope a pure-metadata payload with no text to leak.

**Split triggers — apply when the envelope matches ANY of these:**
- Envelope mentions BOTH a user-text-bearing tool (`chat.postMessage`, `chat.sendPrivateMessage`, `send_email`, `post_social`, social comment/reply, DM) AND a file-write tool targeting an observation log (`drafts-sent.md`, `activity.md`, `patterns.md`, `heartbeats.md`, or any log file that accumulates a history of actions).
- Envelope contains `${block(userText)}` or `${inline(userText)}` AND a subsequent instruction to write user content to a persistent log.
- Envelope carries approved draft text AND instructs the host to both send it externally AND record the send in a log.

Applies ONLY to compound actions with mixed intents. Pure silent persistence (toggle done, rename) and pure compound-autosend with NO logging stay single-envelope.

**GOOD — two sequential calls, user text lives only in the first envelope:**

```typescript
const handleSendReply = async (threadId: string, replyText: string) => {
  // 1. Publish-only envelope — carries the user text, no log instruction
  await sendFollowUpMessage(
    `The user approved this reply for thread @id:${threadId}. Post it via chat.postMessage:\n` +
    `${block(replyText)}\n` +
    `STOP. Do not touch drafts-sent.md in this turn. Do not add any commentary after completing the update.`
  );

  // 2. Metadata-only envelope — no user text anywhere in the payload
  const words = replyText.trim().split(/\s+/).length;
  const tone = classifyTone(replyText); // component-local
  const topic = classifyTopic(replyText);
  await sendFollowUpMessage(
    `Prepend a metadata-only line to drafts-sent.md for thread @id:${threadId}:\n` +
    `@thread:${threadId} @length_words:${words} @tone:${tone} @topic:${topic} @sent_at:(host fills in)\n` +
    `Do not include the reply body. Do not add any commentary after completing the update.`
  );
};
```

**BAD — single envelope mixes user text with log write; host leaks the text:**

```typescript
await sendFollowUpMessage(
  `The user approved this reply for thread @id:${threadId}. Post it via chat.postMessage:\n` +
  `${block(replyText)}\n` +
  `Then prepend to drafts-sent.md: @thread:${threadId} (metadata only, NOT the body). ` +
  `Do not add any commentary after completing the update.`
);
// At execution time the host sees the full envelope — including ${block(replyText)} —
// and often prepends the whole block to drafts-sent.md despite the "metadata only" note.
```

**Grep check at self-review.** Combined patterns like `block(.*(reply|message|body).*).*drafts-sent\.md` in a single template literal MUST return zero matches. If a match is found, refactor into two sequential `sendFollowUpMessage` calls.

### Action Lifecycle Model

Every interactive element (buttons, form submits, toggles) that triggers `sendFollowUpMessage` or `callTool` must implement ALL four states:

| State | UI Representation | widgetState |
|-------|------------------|-------------|
| **Idle** | Button at rest, enabled | `isSending: false, status: 'pending'` |
| **Loading** | Button shows spinner, disabled; item shows subtle overlay | `isSending: true` |
| **Success** | Status badge changes (amber→green), confirmation text visible, item de-emphasized | `isSending: false, status: 'success'` |
| **Error** | Inline error message near action, button re-enabled for retry | `isSending: false, status: 'pending', error: 'message'` |

### Per-Item State Tracking (REQUIRED for list/card UIs)

When the UI shows a list of actionable items (messages, tickets, alerts, tasks), track state per item:

```typescript
interface ItemActionState {
  status: 'pending' | 'success' | 'error';
  isSending: boolean;
  error?: string;
}

// In widgetState:
// itemStates: Record<string, ItemActionState>
```

Initialize state for each item on first render:
```typescript
const getItemState = (id: string): ItemActionState =>
  widgetState.itemStates?.[id] ?? { status: 'pending', isSending: false };
```

### Handler Pattern (REQUIRED for every action)

Every action handler MUST follow this pattern:

```typescript
const handleAction = async (itemId: string) => {
  // Guard against concurrent actions on the same item
  if (getItemState(itemId).isSending) return;

  // 1. Set loading state FIRST (instant feedback)
  setWidgetState(prev => ({
    ...prev,
    itemStates: {
      ...prev.itemStates,
      [itemId]: { status: 'pending', isSending: true, error: undefined },
    },
  }));

  try {
    // 2. Perform the action. For payloads that embed user text,
    //    use the sigil envelope + inline/block helpers described in
    //    "Sendoff format" below.
    await sendFollowUpMessage(
      `Do the thing for item ${itemId}. Do not add any commentary after completing the update.`
    );

    // 3. Optimistic success — update status immediately (don't wait for host)
    setWidgetState(prev => ({
      ...prev,
      itemStates: {
        ...prev.itemStates,
        [itemId]: { status: 'success', isSending: false },
      },
    }));
  } catch (err) {
    // 4. Show error inline on the item
    setWidgetState(prev => ({
      ...prev,
      itemStates: {
        ...prev.itemStates,
        [itemId]: {
          status: 'pending', // revert to pending so user can retry
          isSending: false,
          error: err instanceof Error ? err.message : 'Action failed. Please try again.',
        },
      },
    }));
  }
};
```

### UI Rendering Pattern

```tsx
// Inside your .map() callback for each item:
const state = getItemState(item.id);

return (
  <div className={state.status === 'success' ? 'opacity-60' : ''}>
    {/* Action button with loading state */}
    <button
      onClick={() => handleAction(item.id)}
      disabled={state.isSending}
      data-testid={`action-${item.id}-btn`}
    >
      {state.isSending ? <Spinner /> : t('button.action')}
    </button>

    {/* Status badge */}
    <span className={state.status === 'success' ? 'bg-green-100 text-green-800' : 'bg-amber-100 text-amber-800'}>
      {state.status === 'success' ? t('status.complete') : t('status.pending')}
    </span>

    {/* Success confirmation (visible near the item) */}
    {state.status === 'success' && (
      <div className="text-sm text-green-700 mt-1">{t('status.actionSuccess')}</div>
    )}

    {/* Error message (inline, near the action) */}
    {state.error && (
      <div className="text-sm text-destructive mt-1">{state.error}</div>
    )}
  </div>
);
```

### In-list feedback rows replace toasts (success-state pattern for list views)

When a terminating action resolves an item in a list view (mark done,
dismiss, snooze), the row should be replaced **in its slot** by an
in-list feedback row — not a positioned toast. This pattern is the
agntux-core 6.1.0+ default; toasts are retired for inline iframes.

The reference shape (full implementation in
`briefing-learnings.md` §1.17):

```tsx
const FEEDBACK_FADE_MS = 5000;
const [feedbackRows, setFeedbackRows] = useState<Record<string, FeedbackRow>>({});

const handleResolve = async (actionId: string, label: string) => {
  // ...do the mutation via sendFollowUpMessage...

  // Optimistic feedback row in the action's slot
  setFeedbackRows(prev => ({
    ...prev,
    [actionId]: { kind: 'done', label, addedAt: Date.now() },
  }));
  setTimeout(() => {
    setFeedbackRows(prev => {
      const next = { ...prev };
      delete next[actionId];
      return next;
    });
  }, FEEDBACK_FADE_MS);
};
```

In the list render, the feedback row takes the slot:

```tsx
{actions.map(action => {
  const fb = feedbackRows[action.id];
  if (fb) {
    return (
      <div
        key={action.id}
        role="status"
        aria-live="polite"
        className="px-3 py-2 text-sm text-muted-foreground"
      >
        ✓ {fb.label} · {action.title}
      </div>
    );
  }
  return <ActionRow key={action.id} action={action} />;
})}
```

Three load-bearing properties:

- **`role="status"` + `aria-live="polite"`** so screen readers announce
  the resolution without stealing focus.
- **Preserves scroll position** — the feedback row occupies the same
  slot as the resolved item, so the list does NOT reflow.
- **Counter updates exclude feedback'd ids** — header counts ("3 high
  priority") drop the moment the user clicks Done; don't wait for the
  fade.

Use `useState` (not `widgetState`) for `feedbackRows` — the rows are
ephemeral, and persisting them in `widgetState` would resurrect
expired feedback after a re-render.

**The retired pattern**: positioned `<Toast>` notifications that fade
after 3 seconds. They overlay content the user might be reading,
disappear before the user finishes scrolling, and steal attention
from the list itself. The Toast component is deleted from
agntux-core 6.1.0+; new plugins should not introduce one. If you
need a non-row notification (e.g., a global error not tied to a
specific item), surface it as a sticky banner at the top or bottom
of the list, not as a positioned toast.

### Global Actions (forms, settings, refresh buttons)

For actions without per-item context, track loading/error at the top level of widgetState:

```typescript
const handleGlobalAction = async () => {
  if (widgetState.isSubmitting) return; // guard against double-clicks
  setWidgetState(prev => ({ ...prev, isSubmitting: true, submitError: undefined }));
  try {
    await sendFollowUpMessage(`Do the global thing. Do not add any commentary after completing the update.`);
    setWidgetState(prev => ({ ...prev, isSubmitting: false, globalStatus: 'success' }));
  } catch (err) {
    setWidgetState(prev => ({
      ...prev,
      isSubmitting: false,
      submitError: err instanceof Error ? err.message : 'Action failed. Please try again.',
    }));
  }
};
```

### Sendoff format (sigil envelope, never quoted-string interpolation)

Every `sendFollowUpMessage` is a natural-language instruction the host's LLM will execute — it is the **wire format** between component and host. When the payload embeds user-entered text (title, description, workstream, name, search query), quoted templates like `title='${data.title}'` corrupt the moment a value contains a quote, newline, or backslash (`John's birthday` breaks the format).

Use the same `@key:value` sigils that appear in the file's own schema. The host writes the file using those sigils anyway, so identical shape keeps the host's edit deterministic.

Declare two tiny helpers near the top of your component and use them on every user-authored string:

```typescript
const inline = (s: string | undefined) => (s ?? '').replace(/\r?\n/g, ' ').trim();
const block  = (s: string | undefined) =>
  (s ?? '').split(/\r?\n/).map(l => '  ' + l).join('\n');
```

`inline` flattens a single-line value (titles, names); `block` preserves a multi-line value and indents every line two spaces so it matches the file's continuation format.

Good (sigil envelope, matches tasks.md):
```typescript
await sendFollowUpMessage(
  `User created a new task. Prepend to tasks.md:\n` +
  `@id:${newId} @workstream:${ws} @priority:${p} @due:${d} ${inline(title)}\n` +
  (description ? `${block(description)}\n` : ``) +
  `Do not add any commentary after completing the update.`
);
```

Bad (quoted interpolation — breaks on apostrophes / newlines / backslashes):
```typescript
await sendFollowUpMessage(
  `User created task: title='${data.title}', description='${data.description}'. Do not add any commentary after completing the update.`
);
```

Mirror the sigil envelope in the SKILL.md's "User interaction → file operation" mapping so the host reads an identical shape in both places.

### Mandatory Checklist

Before marking a ticket as complete, verify:
- [ ] Every action button shows a spinner and is disabled while processing
- [ ] Every successful action produces a VISIBLE confirmation (badge change, success text, or visual de-emphasis) — the user must not need to scroll to see it
- [ ] Every failed action shows an inline error message near the action that failed
- [ ] On error, the action button returns to enabled state so the user can retry
- [ ] Header counts or summary text update immediately after actions (if applicable)
- [ ] Per-item state is tracked in widgetState (not a single global flag)
- [ ] Every `sendFollowUpMessage` that embeds user text uses the sigil envelope with `inline`/`block` helpers — no quoted-string interpolation of user-provided values

## Action Feedback — Host Behavior After `sendFollowUpMessage`

**CRITICAL: The component manages all user feedback autonomously.** It shows its own loading spinners, success badges, and error messages via local React state or widgetState. The host must NOT interfere with this feedback.

Every UI-originated write-back arrives as a `sendFollowUpMessage` from the component. Classify the message as **silent persistence**, **compound (autosend)**, or **compound (draft-for-review)** (the SKILL.md should explicitly tag each action with one of the three):

**Silent persistence** — UI-only state change (toggle done, rename, reorder, dismiss, set preference):
1. Call the single slug-prefixed file tool specified in the SKILL.md (`{slug}_write_file`, `{slug}_edit_file`, or `{slug}_prepend_file`).
2. **STOP.** Do not call a render tool. Do not emit any assistant text.

**Compound (autosend)** — the user has already authored or explicitly approved the exact payload (e.g., clicked Send on a draft rendered in a prior step), and now requires a third-party connector, `{slug}_send_email`, or server compute:
1. Execute the connector(s) and/or `{slug}_send_email` call.
2. If applicable, call the file tool (`{slug}_write_file`, `{slug}_prepend_file`, or `{slug}_edit_file`) to persist the result. When writing to an observation log (`drafts-sent.md`, `activity.md`, `heartbeats.md`), persist metadata only — never the verbatim message body.
3. **STOP.** No text, no commentary, no summary.

**Compound (draft-for-review)** — host generates the payload (a reply, an email body, a generated post). The user has NOT yet seen the final content:
1. Generate the content (using user-scoped preferences for writing style, etc.).
2. Call the render tool to show the draft to the user for review.
3. **STOP.** Do NOT call `chat.postMessage`, `{slug}_send_email`, or any other external publish tool in this turn. The external call fires only when the user clicks Send and the component emits a linked `compound (autosend)` action.

**Default rule for publishing verbs.** Any action whose envelope mentions reply, post, send, notify, alert, ping, comment, email, dm, challenge, escalate, respond, or message is `compound (draft-for-review)` UNLESS the user already saw the final content on screen.

In all three cases: do not describe what happened ("I've sent the reply..."), do not suggest next steps ("Would you like to..."), and only re-render when the SKILL.md prescribes it.

In both cases the component already updated its own UI optimistically when the user clicked the action button. Any host commentary after the action would appear BELOW the component, confusing the user about whether the action succeeded.
